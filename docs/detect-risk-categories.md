# 四类风险口径（2.2.2、2.5.3）

首页「四类风险」卡片、检测结果页（`/analysis/results`）和受测应用画像共用一套计数口径，代码在 `apps/api/src/modules/detect-risks/`：

- `sources.ts`：来源定义（类别、名称、权限）；
- `stats.ts`：计数，以及各来源的查询条件；
- 「算一条有效风险」的条件在 `apps/api/src/lib/detect-risk-scope.ts`，任务类别的 SQL 片段在 `apps/api/src/lib/detect-sql.ts`。

四类是模型安全、数据安全、内容安全、应用与环境安全。客户的第五类「保密」本期不做。

## 来源与口径

| 来源 | 类别 | 名称 | 看它要的权限（任一） | 计一条风险的条件 | 时间窗口按 |
|---|---|---|---|---|---|
| `model_file` | 模型安全 | 模型文件扫描发现 | `engine:scan`、`remediation:read` | 发现没被复核判为误报 | 扫描创建时间 |
| `corpus` | 数据安全 | 语料扫描命中 | `corpus_scan:read` | 扫描已完成；命中没被裁判判为误报（`judgeVerdict` 为空也算） | 扫描创建时间 |
| `eval_content` | 内容安全 | 内容评估风险项 | `eval_task:read` | 风险项有严重度、没被复核判为误报、判定不是「通过」；所属任务归内容类 | 任务创建时间 |
| `eval_app` | 应用与环境安全 | 智能体与终端测评风险项 | `eval_task:read` | 同上；所属任务归应用与环境类（智能体测评、终端测评） | 任务创建时间 |
| `service_assurance` | 应用与环境安全 | 服务核验漏洞与基线问题 | `service_assurance:read` | 研判影响状态为受影响或待核验，且有漏洞编号或是配置匹配类基线问题 | 核验创建时间 |
| `ai_component` | 应用与环境安全 | 组件扫描发现 | `engine:scan`、`eval_task:read` | 发现没被复核判为误报 | 扫描创建时间 |
| `asset_discovery` | 应用与环境安全 | 未登记 AI 服务 | `engine:scan`、`platform_setting:read` | 已完成测绘的命中里没对上评估对象的服务（与资产测绘详情页同一判断），按服务地址（协议 + 主机 + 端口）+ 模型名跨次去重 | 测绘创建时间 |

- 严重度分严重、高危、中危、低危、提示五级；没有严重度的（服务核验的部分研判）记「未定级」。「高危」数 = 严重 + 高危。未登记 AI 服务一律记高危。
- 任务归哪一类与 `detectCategoryOfEvalTask` 一致：按 `classifyEvalTask` 判为智能体测评（含终端测评）的归应用与环境，其余归内容。
- 时间窗口：首页按统计周期（本月、近 7 天、全部）取起点，与首页其他卡片同一个 `periodStart`。
- 没有某来源权限的用户看不到该来源，类别合计里也不算它。

## 与现有页面的关系

测试 `apps/api/test/detect-risk-stats.test.ts` 逐条核对。

1. **内容 + 应用与环境（评估类）比首页「安全态势」的风险回复数少终端体检的通过项。**
   - 安全态势卡的风险回复数（`facts.activeFindingTotal`）是本期任务的风险项扣掉误报。
   - 这里另外去掉判定为「通过」的项。终端体检会把通过的检查项也记成风险项，它们不是风险。
   - 同一窗口下：`eval_content + eval_app` = `activeFindingTotal` − 判定为通过的风险项数。
2. **服务核验**（窗口为全部）= 首页「AI 应用组件安全」卡片的漏洞数 + 基线问题数。
3. **模型文件扫描发现** = 各扫描明细里的发现总数之和，减去判为误报的。
4. **语料扫描命中按已保存的命中计。**
   - 一次扫描最多保存 50,000 条命中，超出的只计数不保存。
   - 所以命中超过 50,000 条的扫描，这里比扫描页的「命中总数」少。
   - 接口另返回 `truncatedCorpusScans`（窗口内这种扫描的次数），首页卡片据此提示「N 次扫描命中过多，只计已保存的部分」。
5. **未登记 AI 服务** = 资产测绘详情里「未登记 AI 服务」的行，多次测绘命中同一服务只算一次。
   - 只看窗口内最近 500 次已完成的测绘。超出时接口返回 `discoveryRunsTruncated`，首页卡片和检测结果页提示「资产测绘超过 500 次，只计最近 500 次」。
   - 一次请求只查一次，计数和检测结果取页共用这次的结果（`RiskCounter`）。

## 多租户

- 评估类两个来源用原始 SQL 按任务类别分组，带 `tenantCondition` 租户条件；其余来源走 Prisma 租户查询扩展。
- 「全部租户」视角与首页其他卡片一样汇总所有租户；检测结果页可再按 `?tenantId=` 筛一个租户。
- 未登记 AI 服务只和测绘同租户（或平台共享）的评估对象比对，全部租户视角下也不串租户。

## 受测应用画像（2.5.6）

画像主体是台账里的应用平台，代码在 `detect-risks/profile.ts`、`suggestions.ts`。接口：

- `GET /api/app-profiles`：应用平台列表，每行带关联资产数（不含平台自己）、风险数和高危数。
- `GET /api/app-profiles/:assetId`：画像详情。
- `GET /api/detect-results?profile=<assetId>`、`GET /api/detect-results/stats?profile=<assetId>`：按某个平台的画像范围看检测结果，计数与画像一致；要 `ledger:read`，响应带回 `profile: { id, name }`。

### 范围

- 子树：
  - 平台「包含」的下级平台（最多 3 层）；
  - 这些平台「使用」的模型、组件、软件和「部署于」的服务器；
  - 模型「使用」的组件；
  - 以上模型、组件、软件「部署于」的服务器、终端。
  - 最多 200 个资产（含平台自己），超出时返回 `truncated`。
- 风险只算子树关联到的：平台和模型关联的评估对象、服务器和终端关联终端的终端评估对象、组件的资产键、服务器和终端的 IP、平台访问地址（及按它匹配的服务核验）、关联到子树资产的组合任务子任务建出的记录。时间窗口为全部。
- 资产测绘在有范围时先在库里按 run id、命中的 host、baseUrl 前缀预筛，再按 origin 精确比对；500 次的上限是范围内的最近 500 次。

### 环境、算力和模型的数据来源

- 服务器的系统、CPU、内存、GPU：终端探针上报的优先，探针没有的项用台账服务器属性（`os`、`cpu`、`memoryGB`、`gpu`）兜底。
- 算力卡：这台服务器的探针上报了算力卡（含「没有卡」）就用探针的；没有探针数据时按台账「GPU」一栏解析：
  - 多种卡用「；，、+」分开；
  - 数量写「× 8」「8x」「8 张/块/卡/片」，没写算 1 张，单项最多 64 张；
  - 单卡显存取「80GB」「80G」；厂商按型号里的关键词推断，认不出的记「其他」。
- 算力表：同一台服务器上厂商、型号、显存、驱动都相同的卡并成一行，带数量；型号去掉开头的厂商名和末尾的显存（两样单独成列）。
- 模型的基座模型：模型文件扫描识别出的优先，没有时用台账模型属性 `baseModel`。
- 页面不区分数据来源。没有终端管理读权限的账号看不到探针数据，同样用台账填的。

### 租户与权限

- 与应用台账一样：菜单不进「全部租户」视角；接口在该视角下只读。画像各块（风险、模型的识别结论和最近评估、终端硬件）都只在平台所属租户里取，平台共享的评估对象被别的租户用过也不串过来。
- 风险部分按风险来源的权限过滤。识别结论要模型文件扫描的读权限（`engine:scan` 或 `remediation:read`），最近评估要 `eval_task:read`，终端硬件和算力要终端管理的读权限（`model_target:read`）；没有权限的块为 null，页面显示「—」。

### 处置建议

`suggestions` 每条为 `{ category, source, title, action, count, severity }`，最多 10 条，按 `severity`（这一组里最高的严重度）再按 `count` 排序。`action` 可能为空字符串（组件扫描规则没写处置），页面显示「—」。
